# Backend — Phase 1: Data Layer

This is the first backend phase, built on top of the existing frontend
without changing any UI. Nothing in `app/`, `components/`, `context/`, or
`data/products.ts` was touched — the site still runs exactly as before.
What's new is a real Postgres database + API layer sitting alongside it,
ready to be wired in.

## What was added

- `prisma/schema.prisma` — full data model: `Category`, `Product` (used
  right now), plus `User`, `Address`, `CartItem`, `WishlistItem`, `Order`,
  `OrderItem`, `Review` (scaffolded for Phases 2–5, so there's only one
  migration to run instead of several later).
- `prisma/seed.ts` — migrates the 8 products from `data/products.ts` into
  the database, **plus fixes the category mismatch** found in the frontend
  audit (see below), **plus adds a 9th product** ("Divine Gajalakshmi
  Elephant") — its image was already sitting in `public/img/products/` but
  was never added to `data/products.ts`.
- `lib/prisma.ts` — the shared Prisma client instance (standard Next.js
  singleton pattern).
- `app/api/products/route.ts` — `GET /api/products`, supports
  `?category=<slug>`, `?q=<search>`, `?sort=low|high|rating|featured`.
- `app/api/products/[slug]/route.ts` — `GET /api/products/[slug]`, returns
  the product + its related products (same category).
- `app/api/categories/route.ts` — `GET /api/categories`, returns every
  category with a live product count.

## The category fix

The audit found **three different, mismatched category lists** in the
codebase: `data/products.ts` (`Elephant`, `Tortoise`, `Fish`...),
`constants/categories.ts` (`Vastu`, `God Idols`, `Pooja`...), and a third
hardcoded list inside `Categories.tsx` / `Footer.tsx`. Because of this,
most categories on `/categories` always showed "Coming Soon" even when
matching products existed.

`prisma/seed.ts` uses `constants/categories.ts`'s real shop categories as
the single source of truth and maps every product into one of them:

| Product | Category |
|---|---|
| Royal Silver Elephant | Vastu |
| Sacred Prosperity Tortoise | Vastu |
| Auspicious Twin Fish | Vastu |
| Kamdhenu Cow & Calf | Kamdhenu |
| Balaji Divine Bust | God Idols |
| Sacred Ganesh Shankh | God Idols |
| Divine Gajalakshmi Elephant *(new)* | God Idols |
| Royal Silver Swan Pair | Home Decor |
| Tree of Life Showpiece | Home Decor |

`Gifting`, `Car Dashboard`, and `Pooja` genuinely have **zero** products
right now — that's correct, not a bug. They'll show "Coming Soon" until
real products are added to those lines.

## Prisma 7 note (if you installed after ~Nov 2025)

Prisma released a major version 7 that changed how the database connection
is configured. If `npm install` pulled in Prisma 7.x, you'd have hit this
error on `npm run dev`:

```
error: The datasource property `url` is no longer supported in schema files.
```

This has already been fixed in this project:
- `prisma/schema.prisma` — the generator now uses the new `prisma-client`
  provider (Prisma's newer, faster, "Rust-free" client) with a required
  `output` path, and the `datasource` block no longer has a `url` line.
- `prisma.config.ts` *(new file, project root)* — the database URL used by
  the CLI (`migrate`, `generate`, `db seed`) now lives here instead.
- `lib/prisma.ts` / `prisma/seed.ts` — Prisma 7 requires a driver adapter
  for every database. Both now create a `PrismaPg` adapter (from
  `@prisma/adapter-pg`, wrapping the standard `pg` driver) and pass it to
  `new PrismaClient({ adapter })`.
- Every file that imported types from `@prisma/client` now imports them
  from `@/generated/prisma/client` instead — that's where Prisma now
  generates the client code (previously it went into `node_modules`,
  invisibly). This folder is auto-generated by `prisma generate` (which
  runs automatically via `postinstall`) and is git-ignored, same as
  `node_modules`.
- Added dependencies: `@prisma/adapter-pg`, `pg`, `dotenv`, `@types/pg`.

You shouldn't need to do anything extra for this — just run `npm install`
and everything above happens automatically.

## Running this locally

```bash
npm install                          # also runs `prisma generate` (postinstall)
# add your DATABASE_URL to .env.local — see the comment block already there
npx prisma migrate dev --name init   # creates the tables
npx prisma db seed                   # loads categories + products
npm run dev
```

Then check it worked:
- `http://localhost:3000/api/products`
- `http://localhost:3000/api/products/royal-silver-elephant`
- `http://localhost:3000/api/categories`
- `npx prisma studio` — a GUI to browse the data directly.

## A note on how this was verified

Prisma's CLI needs to download a query-engine binary the first time it
runs (`prisma generate` / `prisma migrate`). The sandbox this was built in
blocks that download (network allow-list doesn't include Prisma's engine
CDN), so `prisma generate` could not be run here — that's a limitation of
*this chat environment only*, not of the code. It will work normally the
moment you run `npm install` on your own machine or on Vercel, both of
which have full internet access.

To still verify the schema and the category-mapping logic actually work
before handing this over, the same tables and seed data were created by
hand-translating `schema.prisma` into raw SQL and running it against a
local Postgres instance inside the sandbox. That confirmed:
- All 7 categories + 9 products insert cleanly (no broken foreign keys,
  no duplicate slugs).
- Category counts came out as expected — God Idols: 3, Vastu: 3, Home
  Decor: 2, Kamdhenu: 1, and Gifting/Car Dashboard/Pooja: 0 (correctly).
- The multi-image product (Sacred Ganesh Shankh) stores and returns all 5
  images.

## Update — frontend is now wired to the database

Every page that used to read from the static `data/products.ts` array now
queries Postgres via Prisma instead. **This means the site will not run at
all until you finish the "Running this locally" steps above** — there's no
fallback to the static file anymore. Specifically:

| File | Before | Now |
|---|---|---|
| `app/collections/page.tsx` | client component, filtered the static array in `useMemo` | Server Component, queries `prisma.product.findMany()`; filters live in the URL (`?category=`, `?q=`, `?sort=`) so the DB query re-runs instead of client-side re-filtering |
| `components/product/CollectionsFilters.tsx` *(new)* | — | small client component that just updates the URL — the search box is debounced (400ms) so it doesn't re-query on every keystroke |
| `app/collections/[slug]/page.tsx` | client component, `products.find(...)` | Server Component, fetches the product + up to 4 related products (same category) from Postgres, plus a `generateMetadata` for real per-product `<title>`/description (SEO) |
| `app/collections/[slug]/ProductDetailsClient.tsx` *(new)* | — | holds all the interactive state (gallery, size, qty, accordions) that used to live directly in `page.tsx` — now driven by props instead of the static import. **Real image gallery works now** — Sacred Ganesh Shankh shows 5 images instead of 1. **Real per-product description** now shows in the Description accordion instead of one generic templated paragraph for every product |
| `app/categories/page.tsx` | client component, counted the static array against `constants/categories.ts`'s hand-written `categoryList` | Server Component, counts real DB rows per category — **this is the actual fix** for the "Gifting"/"Vastu"/"God Idols" categories always showing "Coming Soon" |
| `components/home/CategoryStrip.tsx` | client component, static `categoryList` | Server Component, fetches categories + live Best Seller / New counts from Postgres |
| `components/home/BestSellers.tsx` | client component, rendered **all 8** static products regardless of their `featured` flag | Server Component, queries `where: { featured: true }` — the flag is finally used for something |
| `components/Layout/SearchOverlay.tsx` | client component, filtered the static array in `useMemo` | debounces (300ms) and calls `GET /api/products?q=`, with request cancellation (`AbortController`) so a slow earlier keystroke can't overwrite a newer one's results, and a small spinner for the added network latency |
| `constants/categories.ts` | exported the hand-written `categoryList` (one of the 3 mismatched category sources from the audit) | only exports `virtualBadgeCategories` now (`["Best Seller", "New"]`) — the real category list lives in the DB |
| `lib/adapters.ts` *(new)* | — | `toLegacyProduct()` — converts a DB product (relational `category`, `images[]`, `reviewsCount`) into the flat shape `types/products.ts` already defines, so `ProductCard.tsx`, `CartContext.tsx`, and `WishlistContext.tsx` didn't need to change at all |
| `lib/icon-map.ts` *(new)* | — | maps the icon-name strings stored in `Category.icon` (e.g. `"Gift"`, `"GiElephant"`) back to the real icon component on the frontend |
| `data/products.ts` | — | now unused by any page — nothing imports it anymore. Left in place as a reference/backup; safe to delete once you've confirmed the DB is working end-to-end |

`CartContext.tsx` / `WishlistContext.tsx` are untouched and still use
`localStorage` only — that's correct until Phase 2 (auth) exists to know
*whose* cart it is.

**Still-placeholder, on purpose, not touched in this pass:** the size
selector (4/6/8 Inch) on the product page, the star-rating breakdown and
the two sample written reviews, and the 3 fixed tags (Vastu / Gifting /
Home Decor) shown on every product page regardless of its real category —
all flagged in the original frontend audit, all unchanged here to keep
this pass scoped to product/category data. The `Review` model already
exists in the schema for when you're ready to do reviews for real.
